# Docs workflow

The published documentation is an Astro + Starlight site in `astro-site/`, built
on the shared `@ambiqai/helia-ui` package and deployed to GitHub Pages by
`.github/workflows/docs.yml` on every push to `main`. There is no separate
publish step and no release gate: a docs-only change reaches the site as soon as
it lands on `main`.

## Run it

Node 24 is required; the version is pinned in `astro-site/.nvmrc`. The reference
section is generated from the installed Python package, so a `uv` environment
with the `docs` group has to exist first.

```bash
uv sync --group docs
npm --prefix astro-site ci
npm --prefix astro-site run dev
```

`dev`, `check` and `build` all run `prepare:docs` first, which regenerates the
build stamp, the Reference section, the Modules section and the Examples pages.
None of that output is committed.

Before sending a change:

```bash
npm --prefix astro-site run check      # astro check, strict
npm --prefix astro-site run build      # also runs the agent-bundle postbuild
npm --prefix astro-site run validate   # links, anchors, budgets, contracts
```

`validate` is the one that matters. It reads the built site back and fails on a
broken link or anchor, a missing provenance footer, a page over its size budget,
a public symbol or CLI command absent from the agent bundle, an unmapped legacy
route, a malformed JSON-LD block, a missing SPDX header or a British spelling.

## Where the content lives

| Content | Source |
| --- | --- |
| Home, Getting started, Guides | `astro-site/src/content/docs/`, authored by hand |
| Reference: CLI, Python API, configuration | generated by `astro-site/scripts/build-reference.mjs` |
| Modules: catalog, board matrix, per-module pages | generated by `astro-site/scripts/build-modules.mjs` from the committed snapshot in `astro-site/src/data/{modules,boards}.json` |
| Examples | generated by `astro-site/scripts/build-examples.mjs` from each `examples/<name>/README.md`, front matter and body |
| Module snapshot itself | `scripts/docs/build_module_data.py`, which needs network access to the module repositories |
| Agent bundle: `llms.txt`, `llms-full.txt`, per-route `.md` | `astro-site/scripts/publish-agent-bundle.mjs`, run as npm's `postbuild` |

Hand-written prose that a generator also covers is a bug: a guide should link to
the generated CLI page rather than repeat its option table, because only the
generated one tracks the parser.

## Adding a page

1. Write it as `.md` under `astro-site/src/content/docs/<section>/`, with
   `title` and `description` in the front matter. `description` is not
   optional: the build fails and names every page missing one, because the
   description is what a search result, an Open Graph card and the page's line
   in `llms.txt` all show. A generator that emits pages has to supply one for
   every page it emits.
2. Add it to the section's sidebar in `astro-site/astro.config.mjs`. A page with
   no sidebar entry still builds, but it gets no sidebar trail, so `llms.txt`
   files it under "Other pages" where a reader working through the sections
   never reaches it. `check-discoverability-output.mjs` fails on any route
   there except Home and the 404, which are deliberately outside the sidebar.
3. Run `check`, `build` and `validate`.

Use plain Markdown with Starlight asides unless the page genuinely needs a
component. Every internal link is site-absolute and carries the base path, for
example `/neuralspotx/guides/apps/app-model/`.

## The rendition rule

The discoverability plugin derives each route's `.md` rendition from the MDX
source, not from the rendered HTML. Anything that exists only as a component
prop, a `LinkCard` title or href, a table passed as `rows={...}`, comes out
empty in the rendition an agent reads, and an `export const` body is emitted as
page text.

Two consequences, and both are load-bearing:

- Authored pages are plain `.md`. Reach for MDX only when a component is the
  point of the page, and then check `dist/<route>/index.md` afterwards.
- Generated sections are re-rendered from their models after the build by
  `publish-agent-bundle.mjs`. A new generated section that puts content in props
  has to be taught to that script, or its rendition ships empty.

The example READMEs are inlined at build time for the same reason. An MDX
`import { Content }` of a file outside the site root does render in the HTML; it
is the rendition that comes out blank.

## Transcripts that need hardware

Terminal transcripts are captured runs, never written by hand. These four
commands cannot be captured without a board and a SEGGER J-Link attached, so
`astro-site/src/content/docs/getting-started/flash-and-view.mdx` describes their
output and carries a caution saying it is described rather than captured:

- `nsx probes`
- `nsx flash`
- `nsx reset`
- `nsx view`

Replacing those with real transcripts needs a session on a connected
`apollo510_evb`. Until then, do not invent output for them.

## Maintainer docs

Everything in `docs/maintainers/` is repository Markdown and produces no route.
It is for people working on NSX itself: release mechanics, repo layout, internal
module coverage, board coverage, design decisions and the SDK upstream model.
The published site is for users of NSX. If a page is about how the project is
run rather than how the product is used, it belongs here.
