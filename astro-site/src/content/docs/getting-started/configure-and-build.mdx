Neither of these commands needs a board. Run them from inside the app directory: NSX walks
up from your working directory to the nearest `nsx.yml`, so `--app-dir` is only needed when
you want to act on an app somewhere else.

## Configure

```bash
cd blinky_ap510
nsx configure
```

`nsx configure` does three things in order. It resolves every module constraint in
`nsx.yml` to an exact commit and writes `nsx.lock`. It makes `modules/` match that lock,
cloning anything missing. Then it runs CMake to generate a Ninja build tree under
`build/<board>/`.

Afterwards the app has three things it did not have before:

| Path | What it is |
| --- | --- |
| `nsx.lock` | The resolved graph: every module pinned to a commit. Commit this file. |
| `build/apollo510_evb/` | The generated CMake and Ninja tree, one directory per board. |
| `.nsx/` | NSX's own bookkeeping, including the sync lock file. |

Your source tree stays clean: the generated `.gitignore` covers `build/` and `.nsx/`, and
`nsx configure` writes a `modules/.gitignore` for the modules it re-acquires and a
`cmake/.gitignore` for `cmake/nsx/`.

## Build

```bash
nsx build
```

`nsx build` drives CMake and Ninja. If no build tree exists yet it configures first, so
`nsx build` on a fresh app is enough on its own.

The artifacts land in `build/apollo510_evb/`:

- `blinky_ap510`, the linked ELF. Under GCC it has no file extension.
- `blinky_ap510.bin`, the raw image that gets programmed.
- `blinky_ap510.map`, the linker map.
- `jlink/`, the generated SEGGER command files that `nsx flash` and `nsx view` use.

## Options you are likely to reach for

Both commands take the same core set. Full tables are on the
[`nsx configure`](/neuralspotx/reference/cli/configure/) and
[`nsx build`](/neuralspotx/reference/cli/build/) reference pages.

- A positional `app` argument instead of `cd`. It takes an app name or directory and is
  resolved under `./` and `./examples`, so `nsx build hello_world` from a source checkout
  builds the packaged example of that name.
- `--board` overrides the board in `nsx.yml` for one run, which is how you build the same
  app for a second target.
- `--toolchain` takes `gcc`, `armclang` or `atfe`.
- `--frozen` turns drift between `nsx.yml`, `nsx.lock` and `modules/` into an error
  instead of silently correcting it. `nsx configure --frozen` always checks; on
  `nsx build`, `nsx flash` and `nsx view` it only applies when a reconfigure is needed, so
  run `nsx configure --frozen` as the CI gate.
- `--timeout SECONDS` puts a wall clock budget on each subprocess.

`nsx build` adds three of its own: `--jobs` for parallelism, `--target` to build one
explicit CMake target, and `--update` to re-resolve constraints to upstream tip and
re-vendor before building.

## Starting over

```bash
nsx clean          # run the build system's clean target
nsx clean --full   # remove the build directory outright
nsx clean --reset  # also remove modules/ and .nsx/, back to a freshly cloned state
```

`--reset` prompts before discarding locally modified files under `modules/`; `--force`
skips the prompt. See [`nsx clean`](/neuralspotx/reference/cli/clean/).
