<Band tone="muted" density="compact">
  <SectionHeader
    eyebrow="The model"
    title="Built from modules, not monoliths."
    description="A capability is a versioned module, not a folder you copied out of someone else's project."
  />

  Every module carries a manifest declaring what it depends on and where it runs: the SoCs,
  boards and toolchains it is compatible with. Add one and only that module ships; remove it
  and it is gone. Every module NSX resolves is recorded in `nsx.lock` with a content hash,
  so the set you built today is the set your colleague builds tomorrow.

  <HomeStats />

  The packaged registry lists 50 modules. NSX ships 17 board descriptors across 11 SoC
  families, declaring 3 toolchains between them, and this repository carries 10 example
  apps.

  Read more: the [module catalog](/neuralspotx/modules/catalog/) lists every module and the
  [board matrix](/neuralspotx/modules/boards/) lists every board, with the SoC, tier, SDK
  provider, CPU and toolchains each one declares. [Lock and
  sync](/neuralspotx/guides/modules/lock-and-sync/) explains the lockfile.
</Band>

<Band tone="muted" density="compact">
  <SectionHeader
    eyebrow="Ownership"
    title="Your project, not ours."
    description="What NSX writes is a plain CMake and Ninja project, with everything it depends on sitting beside it."
  />

  `nsx create-app` vendors the modules your app declares into `modules/`, the board into
  `boards/<board>/` and the packaged CMake support into `cmake/nsx/`, then writes a
  `CMakePresets.json` so an IDE can open the project directly. Once `nsx configure` has
  generated the build tree, `cmake --build` drives it with no NSX involvement, and the
  directory copies anywhere. NSX is the fast path through that project, not a dependency of
  it.

  <CodeBlock
    variant="terminal"
    language="bash"
    label="After configure, CMake alone is enough"
    code={`nsx configure\ncmake --build build/apollo510_evb`}
  />

  Read more: [App layout](/neuralspotx/guides/apps/app-layout/) lists every file
  `create-app` writes, which of them are yours to edit, and which NSX regenerates.
</Band>

  <SectionHeader
    eyebrow="Coverage"
    title="One workflow, across the Ambiq line."
    description="The same commands, whichever part you are bringing up."
  />

  NSX ships board descriptors for 11 SoC families: `apollo2`, `apollo3`, `apollo3p`,
  `apollo4l`, `apollo4p`, `apollo5b`, `apollo510`, `apollo510b`, `apollo510L`, `apollo330P`
  and `atomiq110`, whose descriptor today is an FPGA platform rather than silicon. Each
  descriptor declares which of the three toolchains that board builds with, so what a board
  supports is what its descriptor says, not what this page says.

  Read more: the [board matrix](/neuralspotx/modules/boards/) lists all 17 descriptors with
  the SoC, tier, SDK provider, CPU and toolchains each one declares, and
  [Boards and targets](/neuralspotx/guides/apps/boards-and-targets/) covers building one app
  for more than one of them.
</Band>

<Band density="compact">
  <SectionHeader
    eyebrow="Extend it"
    title="Add your own modules."
    description="The packaged registry is a starting point, not the boundary."
  />

  `nsx module init` scaffolds a new module with its manifest, `nsx module validate` checks
  that manifest, and `nsx module register` makes an app-local module visible to the
  resolver. Registry layers in `nsx.yml` let a team point at its own modules alongside the
  packaged ones, so publishing internally does not mean patching NSX.

  Read more: [Custom modules](/neuralspotx/guides/modules/custom-modules/) covers pointing
  an app at your own copy of a module, and
  [Adding a module](/neuralspotx/guides/contribute/adding-a-module/) covers contributing one
  back.
</Band>
