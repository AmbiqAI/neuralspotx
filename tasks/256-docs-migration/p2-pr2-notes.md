## 2. Claims in the current docs that turned out to be wrong

1. **The `view` reset policy is not "Apollo4 secure targets".**
   `docs/user-guide/build-flash-view.md` says Apollo4. `operations/_build.py` defines the
   attach-only set as `apollo3p`, `apollo4l`, `apollo4p` and `apollo510b`. The page now
   names the four and says the set is defined in source rather than derived from the
   family name. (Same correction as PR1 made for Getting started.)
2. **`docs/contributing/sdk-providers.md`: "all provider and wrapper modules resolve to
   v5.2.24" is false.** `registry.lock.yaml` pins `nsx-npu` at `v5.2.25` for the
   `atomiq110` family while the Apollo families stay on `v5.2.24`. Per content map risk 2,
   no SDK revision is stated in prose at all; the page tells the reader to run
   `nsx module describe nsx-ambiqsuite`.
3. **`docs/architecture/dependency-model.md` does not say that optional dependencies are
   never resolved.** `depends.optional` is exposed as a property and used only as a search
   haystack (`module_discovery.py`); nothing traverses it. Three pages now state that
   optional dependencies are metadata, not installs.
4. **`docs/architecture/app-generation-flow.md`'s flowchart does not match the code.** It
   omits template rendering and the post-closure transitive acquisition, and it shows the
   `cmake/nsx` copy in parallel with the manifest write. The page now lists the ten stages
   `_create_app_body` executes, in order.
5. **`docs/user-guide/app-layout.md` omits `cmake/presets/` and `.gitignore`**, both of
   which every generated app has, and it shows `boards/` unconditionally. PR1 established
   that `boards/` appears only after bootstrap; this page carries that through.
6. **`docs/user-guide/system-init.md` documents `nsx_system_init()` while the generated
   app calls `nsx_core_init()`.** Both exist. A bootstrapped app carries
   `modules/nsx-ambiq-sdk/modules/nsx-core/includes-api/nsx_core.h` and `nsx_system.h`.
   The page now presents them as two layers and says which one the template uses, rather
   than documenting only the one the reader will not see in their `main.c`.
7. **`docs/architecture/sdk-provider-model.md` presents `NSX_AMBIQSUITE_VERSION` as an SDK
   version.** `nsx_sdk_providers.cmake` sets it to the literal `stable`. The page calls it
   the release channel.
8. **`docs/user-guide/sdk-provider-selection.md`'s wrapper list omits `nsx-ambiqsuite`
   itself**, which is the provider module every board profile pins. The merged page names
   the provider separately from the four wrappers.
9. **`docs/architecture/metadata-model.md` never mentions `board.yaml`**, although it is
   one of the four schemas and has a generated reference page. The concepts page includes
   it.
10. **`docs/user-guide/python-api.md` documents 12 of 80 exported names** and marks none of
    them provisional. The guide states the provisional status once and links the generated
    reference for the surface.

Two claims checked and kept: the four attach-only SoCs really are attach-only by default
(`operations/_build.py`), and `nsx.yml` really does parse a `source.git` block that the
resolver then rejects (`module_registry/_profile.py`), which the lock and sync page quotes.

## 5. Two mechanical findings worth carrying forward

**The Markdown rendition is derived from the MDX source, not from the HTML.** Component-only
content does not survive into `dist/<route>/index.md`, which is the surface agents read.
Two consequences applied here:

- Every hand-written Guides page is plain `.md`. No page in this PR uses `export const`,
  a JSX comment or a component.
- The Guides index uses a Markdown link list per group rather than a `CardGrid` of
  `LinkCard`s, so every route it offers is in the rendition.

Verified after the build: no `export const` or `{/*` in any `dist/guides/**/index.md`, and
for all 35 Guides pages the set of internal links in the rendered `sl-markdown-content`
is a subset of the links in the rendition. The rendition absolutizes some links to
`https://ambiqai.github.io/neuralspotx/...`, which is why a naive string comparison
reports false positives.

**Examples had to be generated rather than imported.** An MDX
`import { Content } from '../../../../../../examples/<name>/README.md'` does resolve and
does render in the HTML, which contradicts the assumption that Astro cannot reach outside
the site root. But the rendition of such a page contains the title and nothing else. So
`astro-site/scripts/build-examples.mjs` inlines the READMEs at prepare time instead:

- Reads front matter from `docs/examples/*.md` and bodies from `examples/<name>/README.md`.
- Writes 11 gitignored pages into `src/content/docs/guides/examples/` plus
  `src/data/examples-sidebar.json`, in the same `prepare:docs` pass as the reference and
  module generators.
- Fails the build if a documented example has no README, if a stub is missing `title`,
  `tier`, `summary` or `status`, or if a stub declares an unknown tier.
- Carries a one-entry `QUOTED_TERMS` opt-out list for spellings an example author wrote
  that the site's American-English check rejects (`Initialises` in `hello_world`). A new
  British spelling in a README fails `npm run validate` until someone adds it, which keeps
  the opt-out deliberate.
- Strips each README's own H1 so the page has one, and changes nothing else in the body.

Nothing about tier, status, capabilities or `boards_tested` is hand-entered. Every table
cell is the example author's own front matter, and the overview says so in those words.

**This couples the site to `docs/examples/`.** Those ten stubs carry the only copy of the
front matter, and #261 removes the MkDocs tree. See section 7.

## 7. For the owner

1. **`STACK_SIZE` units are ambiguous in this repository.** `boards/*/board.cmake` comments
   it as bytes; `docs/user-guide/startup-and-linker.md` documents the SDK startup array as
   `uint32_t` words, which would make the same value four times larger. The consumer is in
   the vendored `nsx-core` module. The page states no unit until this is settled.
2. **The generated `nsx.yml` reference documents `source.git` as accepted.**
   `scripts/docs/config_schema.yaml` lists `modules[].source` as "exactly one of path,
   vendored or git", but `module_registry/_profile.py` raises on a git source. The
   schema manifest is #258's file and was not edited here; the Guides page states the
   rejection and quotes the error.
3. **Example front matter lives only in `docs/examples/*.md`,** which #261 deletes. Before
   the cutover it needs a home that survives: either front matter in each
   `examples/<name>/README.md`, or a small data file in `examples/`. The generator reads
   whichever it is told to; the move is a decision, not a code change.
4. **`nsx-timer`, `nsx-interrupt` and similar SDK-internal modules have no catalog page.**
   The SDK providers page says so in a note. `nsx-harness`, named in the P1b handoff as a
   fourth non-registry dependency, does not appear in the current registry or code.
